# 依赖分层与架构契约

> 起因：评估 `dependency-cruiser` 是否适用于本项目。
> 结论：**不适用**（JS/TS 专用），用 Python 等价物替代，并已在项目里落地。

---

## 一、为什么不用 dependency-cruiser

| 项 | 说明 |
| --- | --- |
| 它是什么 | JS/TS/CoffeeScript 的**依赖分析与架构规则校验器**（`sverweij/dependency-cruiser`，MIT，6.8k stars） |
| 能做什么 | 依赖图（dot/svg/html/json）、循环依赖检测、孤儿模块、用 `.dependency-cruiser.js` 写"禁止 A 依赖 B"的规则、afferent/efferent 耦合度、CI 违规基线 |
| 为什么不用 | **只解析 ES6 / CommonJS / TypeScript**，对 `.py` 文件直接忽略。本项目是纯 Python + PySide6，装了也扫不出任何东西 |

它解决的问题对 Python 项目同样重要，所以用等价物补上：

| dependency-cruiser 的能力 | Python 等价物 | 本项目是否已用 |
| --- | --- | --- |
| 循环依赖检测 | `desloppify` 的 `cycles` detector | ✅ 已跑：**0 个循环** |
| 孤儿模块/死代码 | `desloppify` 的 `orphaned` detector / `vulture` | ✅ 已跑：10 个孤儿文件 |
| 架构规则（禁止 A→B） | **`import-linter`**（本项目已接入） | ✅ 见下 |
| 依赖图可视化 | `pydeps` + graphviz（未装，按需） | — |
| 耦合度指标 | 自建 `tools/dev/code_metrics.py`（跨包依赖计数） | ✅ 已跑 |

## 二、本项目的实际依赖方向

用 AST 统计（排除 tests/tools/docs/.local）：

| 从 | 到 | 次数 | 判断 |
| --- | --- | --- | --- |
| ui → utils | 88 | 正常（界面用工具） |
| workers → utils | 44 | 正常 |
| ui → censor | 34 | 正常（界面调业务） |
| ui → workers | 29 | 正常 |
| automation → utils | 27 | 正常 |
| **censor → utils** | 17 | 可接受（业务用工具） |
| **utils → censor** | **6** | ⚠️ 唯一的"反向" |
| automation → censor | 1 | 正常 |
| ui → automation | 1 | 正常 |
| workers → automation | 1 | 正常 |

### 那 6 处 utils → censor 是什么

```
utils.data_profile      -> censor.store           (l.68, l.113)   读判定结果做统计
utils.media_upgrade     -> censor.numbering       (l.247)         解析番号
utils.media_upgrade     -> censor.releases.models (l.248)         番号归一化
utils.replacement       -> censor.numbering       (l.80)          解析番号
utils.replacement       -> censor.releases.models (l.81)          番号归一化
```

**判断：不是设计错误。** 三点依据：

1. 全部是**函数内延迟导入**（不是模块顶层），不会造成导入期循环；
2. 借用的都是**叶子模块**（编号解析、数据类型），没有副作用，不含业务编排；
3. `censor.numbering` 本质是"文本解析工具"，只是历史原因放在了 `censor` 包里。

**如果将来要彻底消除**，正确做法是把 `censor/numbering.py` 与 `censor/releases/models.py`
里被外部复用的部分**下沉到 `utils/`**，而不是让 `utils` 到处 import 业务包。这是一次独立的小重构，不急。

## 三、已落地的架构契约

文件：项目根 `.importlinter`

```ini
[importlinter]
root_packages = ui, censor, utils, automation, workers

# 1) 业务/工具层不得依赖界面层
[importlinter:contract:no-ui-imports]
type = forbidden
source_modules = censor, utils, automation, workers
forbidden_modules = ui

# 2) 业务层不得依赖后台任务层
[importlinter:contract:no-worker-imports]
type = forbidden
source_modules = censor, utils
forbidden_modules = workers, automation

# 3) 非页面模块不得依赖具体页面
[importlinter:contract:no-page-imports]
type = forbidden
source_modules = censor, utils, workers, automation
forbidden_modules = ui.pages
```

**当前结果**：

```
Analyzed 147 files, 495 dependencies.
业务/工具层不得依赖界面层    KEPT
业务层不得依赖后台任务层      KEPT
非页面模块不得依赖具体页面    KEPT
Contracts: 3 kept, 0 broken.
```

**契约是真能拦住的**（自检）：临时加一条 `utils 不得依赖 censor`，工具立刻报
`BROKEN` 并列出精确到行号的 5 条违规 —— 说明前面 3 条 KEPT 不是"空跑"。

## 四、怎么用

```bash
# 跑一次契约检查（快，<2 秒）
.venv/Scripts/lint-imports.exe

# 或
.venv/Scripts/python.exe -m importlinter
```

**建议接入打包门禁**：`scripts/build_release.py` 的验证步骤里加一条，
这样"谁把 ui 反向塞进 censor"会在出包前就被拦住。

## 五、不要做的事

- **不要**为了"更漂亮的分层"把 `censor` 拆成 `censor_core` / `censor_ui` —— 现在的
  `censor`（纯逻辑）/ `ui`（界面）边界已经清楚，再拆只会增加跨包 import。
- **不要**写 `layers` 型契约（要求严格单向）。实际存在 `utils → censor` 的有意复用，
  强行套 layers 会逼出一堆 `# type: ignore` 式的规避写法，反而更糟。
  用 `forbidden` 精确禁"真正不该发生的方向"才是有效约束。
