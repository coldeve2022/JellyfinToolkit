## 五、主观维度（工具没评，我来评）

Desloppify 的 strict 分只有 21.1，是因为 75% 权重的主观维度**未评估**（不是代码差）。按它的评分维度，我人工给判断：

| 维度 | 判断 | 依据 |
| --- | --- | --- |
| 命名一致性 | **好** | 中文注释 + 英文标识一致；`search_keyword` vs `match_token` 这类"概念分离"命名清楚 |
| 抽象质量 | **中** | 好：`version_level` / `ReleaseSource` / `next_review_target` 都是干净的纯函数；差：页面类没有分层 |
| 模块边界 | **中偏弱** | `censor/` 与 `ui/` 分层清楚，但 **ui 直接读 `censor` 内部结构**（`row.report.best.best_magnet` 这类），且**存在两套替换链**、两套 `_default_db_path` |
| 错误处理一致性 | **弱** | 有三种风格并存：抛 `ValueError`（service）、返回 `(ok, msg)`（probe）、静默 `except: pass`（transport 5 处） |
| 契约/类型安全 | **中** | 大量 `dataclass`，但页面层用裸 dict 传状态（`self._batch_review_navigation` 就是） |
| 测试质量 | **好** | 1,700+ 用例；关键纯函数都有单测；但 GUI 用例在全量跑时不稳定（见第七节） |

## 七、工具误报核对（不能盲信）

Desloppify 报了两条 `phantom_read`（`transport.py:267` 的 `parts['http']` / `['https']`），看起来像 KeyError 风险。**实测是误报**：

```python
parts = dict(item.split("=", 1) for item in server.split(";") if "=" in item)
server = parts.get("https") or parts.get("http") or ""
```

用的是 `.get()`，缺键返回 `None`，不会抛异常。工具把"字典里没有这个 key"直接当成了问题，没有区分 `.get()` 与 `[]`。

**另外一条真问题**（工具也报了，但值得单独说）：
`censorship.py:1583` 把 `after` / `context` / `epoch` / `positions` / `report` / `selected` 六个 key 写进 `_batch_review_navigation` 后再无读取 —— 这是**半废弃逻辑没清**，不是误报。

## 八、整改路线（按性价比排序）

### P0：先止血（1–2 天，风险低）

| 动作 | 具体 |
| --- | --- |
| 清死代码 | 删 `_batch_review_navigation`（或补上读取）；清 53 处未被引用的顶层函数（先确认不是公开 API） |
| 统一"可见行"判定 | 把 `_matches_filter` / `_advance_review` / `_refresh_stats` 三处口径合并为**一个** `visible_rows()`；这是两个 bug 的共同根源 |
| `except: pass` 补日志 | `transport.py` 5 处；否则下次代理问题还是查不到 |
| `.desloppify/` 进 `.gitignore` | 本地状态不该入库 |

### P1：拆上帝类（3–5 天，风险中）

**检测页**（1744 行 → 目标 4 个文件，每个 <400 行）：

1. `ReviewSession`：`_current` / `_review_overrides` / 批次状态，唯一真相来源
2. `ReviewFilters`：视图/结论/喜欢/播放 + `visible_rows()`
3. `ReviewActions`：标记/撤回/批量/跳转（复用已抽好的 `next_review_target`）
4. `CensorshipPage`：只剩拼装与转发

**找无码页**（1089 行 → 目标 4 个文件）：

1. `ReleaseTableModel`：列、颜色、排序、`UserRole` 载荷
2. `ReleaseActions`：复制/送替换/送 Lada/打开页（现在混在页面里）
3. `ReleaseFilterBar`：搜索 + 三个下拉 + 高级筛选入口
4. `CensorReplacePage`：拼装

### P2：拆巨型函数（2–3 天，风险中）

| 函数 | 拆法 |
| --- | --- |
| `censor/service.py::probe`（215 行 / CC64） | 拆成 `_load_cached` / `_run_detectors` / `_fuse` / `_persist` 四段，主函数只做编排 |
| `censor/mosaic_cv.py::_analyze_stream`（152 行 / CC51） | 抽出 `_normalize_frame` / `_score_frame` / `_aggregate` |
| `censor/releases/service.py::lookup`（128 行 / CC55） | 拆成 `_fan_out`（并发）/ `_merge`（聚合）/ `_decide`（判定） |
| `_setup_ui`（314 / 174 行） | 按区域拆 `_build_toolbar` / `_build_filters` / `_build_table` / `_build_right_panel` |

### P3：清概念重复（1–2 天）

| 重复 | 处理 |
| --- | --- |
| 两套替换链（`execute_replacements` vs `MediaUpgradeService`） | 至少把"转封装 + 身份校验"抽成共享段；长期合并 |
| `_default_db_path` 两份 | 提到公共模块 |
| 新旧筛选判定并存（`_favorite_matches` vs 规则引擎 `favorite`） | 让页面快捷筛选也走规则引擎，避免两套语义 |

### 不建议做

- **不要为了 desloppify 分数去重构**。它的 strict 分 21.1 主要来自"主观维度未评估"，不是代码差；跑一次 `review` 分数就会大幅变化。分数只是体检表，不是目标。
- **不要动 `censor/` 的算法层**（`mosaic_cv` / `sampling`）来"降低复杂度"。那些分支是真实场景（变帧率、非零起点、色彩空间），拆错会掉准确率。
