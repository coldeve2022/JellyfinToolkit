# 检测与替换检索：数据结构、互通问题和本次重构

检查日期：2026-10-31。依据当时工作目录的代码和 SQLite 只读结构检查。下文先说明修改前的结构，再说明本次代码改动。

## 1. 先说结论

视频像素化检测和替换版本检索的核心数据，通常确实存放在**同一个 `data/censor.db` SQLite 文件**里。但是它们使用不同的表、不同粒度的主键和不同的状态模型。

“同一数据库文件”不等于“所有数据已经统一管理”。当前还有单独的用户状态 SQLite、工作区 JSON 和缩略图目录。两个页面的数据主要靠 Python 服务层关联，既没有覆盖全部字段的统一 SQL 视图，也没有文件与作品之间的独立关系表。

保留文件级检测、作品级检索这两种粒度是合理的数据建模。问题出在关联、投影、字段解释与筛选被分散到了页面和规则引擎中。

## 2. 先确认自己用的是哪份数据

正常启动使用的不是必然位于源码旁边的 `data`。路径优先级是：`--data-dir` / 当前进程环境变量 → 程序目录 `data-profile.json` 里的本地选择 → 程序文件夹内的默认资料库。

换代码目录后看到的数据未必跟着变，这是持久资料库复用机制的设计，不是故障。只读核对：

```bash
python main.py --profile-info
```

它会显示实际生效的库根目录、`profile.json` 身份与数据库状态，不写入任何东西、也不触发迁移。

## 3. 像素化检测怎么存

### `censor_probe`：当前路径对应的检测记录

主键为 `path`。一个文件一行，不是一个作品一行。同一作品的两个副本会有两条检测记录。

| 字段组 | 字段 | 含义 |
|---|---|---|
| 文件 | path, size, mtime, duration | 路径、大小、修改时间、时长 |
| 作品线索 | number, provider | 从文件/元数据解析的编号和来源线索 |
| 当前检测结论 | state, confidence, needs_review, reason | 状态、置信度、是否待复核、解释 |
| 详细证据 | evidence | JSON 数组；不同证据来源及其结论 |
| 复核画面 | candidates | JSON 数组；采样时间、截图/裁剪图路径等，**不是网络候选版本** |
| 画面分数 | visual_score | 画面检测原始最高分，不应当作 0–1 概率 |
| 执行 | elapsed, error, status | 耗时、错误、完成/部分完成/失败/取消 |
| 有效性 | file_identity, analysis_signature | 文件版本身份、检测参数/算法签名 |
| 检测统计 | sampled_frames, analyzed_frames, detector_runs | 采样数、实际分析数、各检测器运行 JSON |
| 更新时间 | updated_at | 当前行更新时间 |

`state` 描述本地文件的画面结论。`status` 描述检测有没有完成，两个字段不能合并。

文件身份由文件大小、纳秒级修改时间和采样内容哈希组成。严格复用检测缓存还需要匹配分析签名、完成状态等；只比较路径是不够的。截图文件位于资料库的 `data/censor_thumbs`，数据库保存它们的引用。

### 人工标记不是只有一张表

| 表 | 主键 | 职责 |
|---|---|---|
| censor_label | path | 路径级当前标记的兼容投影 |
| censor_label_history | (path, file_identity) | 文件版本对应的人工标记、备注和时间 |
| censor_label_revocations | (path, file_identity) | 此文件版本的标记已撤销 |
| censor_label_events | id | 标记/撤销的操作事件记录 |

`censor_label_history` 虽然叫 history，但相同路径与身份是更新同一行，并非每次操作追加一行。逐次操作由 events 表记录。

因此，权威人工结论应按 `path + file_identity` 查询，并排除撤销记录；不能只看路径级兼容表，也不能只相信 `censor_probe.evidence` 里某次写入的人工证据副本。

### 队列和外部同步

`pixelation_queue` 保存按文件身份派生的任务键、路径、任务状态、优先级、原因、错误、更新时间和人工请求标志；`pixelation_sources` 保存待展开输入源及状态。这些是调度数据，不是画面结论。

`censor_metadata_sync` 保存希望向 NFO/Jellyfin 同步的结果、修订号和端点执行状态；`censor_metadata_receipt` 保存按路径、文件身份、端点归属的同步回执。它们不能替代检测结论或人工标记。

`toolkit_schema_versions` 目前按 component 登记结构版本；检测存储已有升级前备份和事务迁移逻辑，但并不是所有子模块都统一接入了这套迁移器。

## 4. 替换版本检索怎么存

它也写进 `censor.db`，但由 `ReleaseStore` 管理独立的表。

| 表 | 主键 | 内容 |
|---|---|---|
| release_report | number | availability、signature、report JSON、queried_at |
| release_attempt | number | 最近一次检索尝试的 report JSON 和时间 |
| release_lookup_queue | number | priority、note、status、updated_at |

这里的 `number` 是规范化编号。例如 `ABC-123`、`abc_123`、`ABC 123` 会成为同一个键 `ABC123`。它描述作品，不描述某个本地文件，所以同一作品多个文件共享一个检索报告。

报告 JSON 里面保存作品编号、可得性、耗时、执行状态、备注、各站点状态和候选列表。每个网络候选又有来源、标题、页面链接、日期、时长、分类、判定置信度和磁链；磁链带 URI、名称、大小 `size_mb`、文件数、日期和标签。

注意以下同名概念并不相同：

- 检测的 `state/confidence`：本地文件结论及置信度；检索的 `availability/uncensored_confidence`：网络候选可得性及其依据置信度。
- 检测的 `candidates`：复核画面；检索的 `candidates`：网络条目。
- 检索 `availability`：确有、疑似、未见、未知；检索 `status`：完成、部分完成、失败、取消。失败不能伪装成“未见”。
- 磁链原始大小使用 MB；筛选数值统一转换为字节，支持输入 MB/GB/TB。

最近一次尝试可能失败，但旧的成功报告仍保留。列表会选择时间较新的尝试展示当前执行情况；这不等于删除旧报告。`release_attempt` 只保留每个编号的最近尝试，并不是完整检索历史。

## 5. 喜欢、播放状态和筛选配置在哪里

### `jellyfin_review.sqlite3`

这是另一份 SQLite 文件，位于同一资料库的 data 目录。

现有磁盘数据在检查时只有旧格式 `snapshots(context PRIMARY KEY, payload JSON)`。当前代码已支持下一次成功同步时，在同一事务中发布关系投影：

- `user_state_schema`：结构版本。
- `user_state_snapshots`：context、revision、updated_at、legacy_digest、row_count。
- `user_state_items`：主键 `(context, path)`；原始路径、item_id、user_id、remote_path、mapped、name、favorite、played、play_count、playback_ticks、has_progress、ambiguous、tags、genres。

关系投影已有 `(context, favorite)` 和 `(context, played)` 索引。兼容读取仍以旧 JSON 的摘要校验为依据，避免旧版本写入后新投影变成过期数据。**仅打开页面不会把旧快照迁移成新表**。

context 由服务器、账号、凭据指纹、数据源模式/数据库路径、媒体库范围和路径映射等共同决定。自动数据源还需要已确定的来源身份。不能随便读取“最近的一份快照”，否则可能串账号或串范围。

### `workspace_preferences.json`

搜索词、下拉选项、列布局、分栏、规则、规则组合方式等属于 UI 偏好，保存在 JSON 中，不写入检测事实表。本次新增的列取值筛选也存这里。

工作区偏好当前按页面键保存，并非完整的账号/范围命名空间。切换资料库目录会换偏好文件，但同一目录内切换账号仍可能保留同样的显示条件，这是后续可以改进的地方。

## 6. 两页原来怎样互通，哪里有问题

原来的替换清单生成链路是：

1. `VerdictStore.confirmed_censored()` 选出人工确认且文件身份仍匹配的文件。
2. 页面按规范化编号聚合文件路径。
3. `ReleaseStore.get_many()` 和 `latest_attempts()` 批量补上检索报告。
4. 页面另外读取用户状态快照，按规范化路径匹配喜欢/播放。
5. 页面快捷筛选执行一套判断，高级规则引擎再执行另一套判断。

检测页则有自己的文件级 `ReviewQuery`、快照控制器及历史投影。库文件统一了，查询事实与状态解释并没有完全统一。

本次复现的问题包括：

| 问题 | 原因 | 修复 |
|---|---|---|
| 历史页已确认，替换清单不出现或保留旧证据 | confirmed_censored 依赖路径级候选及 probe 内人工证据副本 | 共用历史页按文件身份关联的人工标记投影 |
| 一份副本未喜欢，另一份未知时，两种筛选不同结果 | 页面与规则引擎各写聚合 | 共享文件级状态函数和作品聚合 |
| 已同步，替换页仍提示未同步 | 新建服务丢失自动来源的已解析身份 | 同目录、同 context 复用服务，订阅快照更新事件 |
| 预览计数比实际可见多 | 只计算高级规则，漏了关键词、快捷条件和临时范围 | 预览与显示共用 ReleaseQuery |
| 数值填错仍能应用，结果奇怪 | 非法数值被转换为零 | 编辑时明确报错；不启用非法条件 |
| “命中来源”会匹配超时站点 | 把 sources 执行记录也当成命中 | 命中来源只统计候选，另设“尝试过的来源” |
| 隐藏行还能拖出、刷新又被选中 | 当前行回退和恢复选择忽略隐藏状态 | 可见性检查覆盖选择、拖出和刷新恢复 |
| 检查页送来几个文件，批量准备却扩到全清单 | 范围判断没有贯穿批量准备 | 当前筛选与接收范围同时约束目标 |
| 无编号的文件被合并成一部 | 所有空编号使用同一个聚合键 | 使用路径派生键分别保留 |
| 最大磁链显示和筛选不一致 | 显示最佳候选的磁链，筛选却取全部候选最大值 | 同一“全部候选最大大小”口径，大小/时间按数值排序 |

作品聚合的现有统一语义：任一副本喜欢则作品喜欢；全部明确未喜欢才是未喜欢。全部副本已播放才算已播放；任一未完成副本在播则算播放中；全部明确未播才算未播放；其余未知。未知不会被默认当作否。

检测页计数单位是文件，替换页计数单位是作品；例如 3 个文件合成 1 个作品，这种数量差异本身是正常的。

还有范围差异：替换页的基础清单来自本资料库全部有效人工确认记录，检测页可能只加载当前选定的文件或媒体库范围。用户状态快照按其 context 隔离，并不意味着所有检测记录已经具备可按媒体库 ID 查询的成员关系；这也是后续文件/作品关系与统一范围查询需要补齐的部分。

## 7. 本次筛选模块怎么重构

已移除 `ui/release_filter_dialog.py` 和运行时调用，旧文件及其专属测试已一并移除，不再保留入口。

新结构：

- `censor/release_query.py`：作品行投影 `NumberRow` 与纯查询 `ReleaseQuery`。
- `censor/release_filter.py`：集中定义字段、取值与运算符；输入校验。
- `utils/media_review_query.py`：文件状态解释与作品状态聚合共用。
- `utils/jellyfin_review.py`：按资料库目录与配置 context 隔离的共享快照服务。
- `ui/release_filters.py`：页内规则编辑器、表头筛选入口和列取值菜单。
- 检索页负责绑定控件和展示，不再自己解释一套喜欢/播放规则。

操作方式：

1. 点表头右侧箭头，搜索并勾选本列取值；右键表头也可以打开。
2. 同列选择多个值取并集，不同列取交集；全不选会显示零条，清除此列才解除该列限制。
3. 复杂比较直接在页内选择字段、运算符和值，添加后立即生效。点击已添加条件可编辑，选中后可删除；自定义条件可 AND/OR 组合。
4. 当前规则和列限制直接展示，可清空。表头菜单计数叠加其他条件，但排除本列自身的取值限制。
5. 新增可见的喜欢/播放列；查询词也能搜索快照中的名称、标签和类型。
6. 增加检测结论置信度、画面原始分数、检测耗时、检索执行状态等字段。检测置信度是有效融合结论的置信度，可能包含人工证据，不等于纯视觉概率。
7. 查询未查、重查当前清单和 CSV 导出遵循当前筛选；检查页送来的范围同时限制批量检索。

旧有效规则恢复到页内；不合法的旧条件明确提示未启用。旧预设数据保留在偏好文件中，本轮没有重新提供预设管理弹窗。这里没有引入新的第三方依赖。

## 8. 字段现在能不能互相检索

本次已经让替换检索查询同时访问：本地路径、作品编号、当前作品的检测记录、网络检索报告、同一上下文的喜欢/播放快照。当前显示、计数和目标选择共享查询口径。

但这仍不是“任意 SQL 字段双向自由关联”：检测页尚未具备按所有网络候选属性反向筛选的统一查询接口；JSON 深层字段也没有全部转成带索引的列。不能把本次查询层重构描述为已完成全库关系化改造。

## 9. 数据库进一步怎么优化

### 第一步：延续本次统一读取，先确保事实一致

人工标记只认身份级权威记录；页面不缓存另一份可独立修改的标记。文件路径规范化、编号规范化、未知状态和聚合规则统一。保留检测状态与检索状态的命名空间，避免强行共用一个 state 字段。

把快照读取、账号隔离和数据目录解析收敛为共享服务。本次完成了与这两页直接相关的部分；其他页面可逐步接入。

### 第二步：显式建立文件与作品关系

建议新增稳定的 media_file 主体与 work 主体，通过 file_work 关系表连接，而非每次从 probe.number 临时推导。保留原始编号、规范化编号、关联来源和修订号；无编号文件保持独立身份，编号改变应更新关联。

人工标记仍按文件版本保存，网络报告仍按作品保存；不要把多个文件的证据复制进作品报告。这样可以从作品回查文件，也可以从检测文件关联作品报告，并明确处理改名、移动和多副本。

### 第三步：为常用筛选提供带索引的只读投影

优先投影作品键、候选数、磁链数、最大磁链字节数、检索执行状态、结果时间；保留原始 JSON 便于兼容和诊断。候选/磁链可再拆为子表，以支持按同一候选同时约束来源、大小与置信度，避免多个候选各满足一个条件却被误认为同一个候选满足全部。

检测侧可索引规范化作品键和常用复核字段；用户状态已支持 context+favorite/played 索引。大型列表再考虑把内存查询下推成 SQL 或采用 Qt model/proxy，分页、虚拟化和批量投影，而非继续扩充 QTableWidget。

### 第四步：迁移、时间与偏好一起治理

统一 component 迁移入口和结构版本；每次迁移使用一致性备份、单事务、回填数量/身份关联校验。对旧 JSON 保留兼容读取窗口。时间字段统一为 UTC 时间戳或规范 UTC 文本，显示时转本地时间。

工作区偏好按资料库标识及必要的账号/范围键隔离；记录查询模式版本，旧条件升级有明确提示。

**不建议为了“看起来统一”马上把所有 SQLite 文件塞成一个大表。** 独立的用户快照库可以继续存在，关键是统一上下文、明确关系、避免两份可写事实。若未来必须跨库 SQL 联查，可以用只读 ATTACH 和显式上下文条件；跨库事务发布则需要额外设计。

## 10. 验证边界

测试全部在临时资料库和合成文件上执行。覆盖真实 SQLite 的人工标记身份关联、作品聚合、最新尝试与旧成功报告共存、未知状态、快照事件传播、列多选/清空/取消、输入校验、规则编辑/恢复、隐藏行、排序更新、批量范围与 CSV 导出。

另做了离屏 GUI 构造和合成数据渲染。没有对真实媒体执行检测、下载或替换；没有修改或合并真实资料库。网络站点可用性不属于本次离线验证结论。

最终验证：190 项相关测试（包括全部页面构造/导航冒烟）通过；23 项新增回归单独复跑通过；本次修改文件 ruff 检查通过，git diff 空白检查通过。
