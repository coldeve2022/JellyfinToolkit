# 稳定资料库与启动恢复修复

用户希望升级后持续读取同一数据库，不再依赖每版启动 BAT。沿用已授权自行处理细节的范围；保留真实数据，不覆盖合并两个独立库。

## 根因证据

- 项目 data/censor.db：2602 扫描、1414 人工确认；APPDATA 默认库：4 扫描、0 人工确认，均只读检查正常。
- config 当前区分源码项目目录与冻结程序用户目录，BAT 只覆盖路径，没有进行格式导入。
- 检测页首次只恢复最多300待办并切TODO，完整历史虽已支持后台加载但不会自动执行。

## 采用的设计

1. 在不随版本变化的用户位置保存 data-profile.json，登记实际默认资料库根目录。既有资料库直接登记原位置，不复制5GiB证据、不按版本导入导出；新安装仍使用标准用户数据目录。显式data-dir/环境变量/便携模式保持优先、隔离且不重写全局登记。
2. 首次仅在程序有限父级及标准用户位置查找现有库。唯一库可直接接续；多个有数据的库显示路径和记录数供选择，绝不按日期猜测覆盖合并。登记位置不可访问或登记损坏时停止并说明，不静默创建空库。
3. 启动在创建业务服务之前完成资料库定位；所有模块共用同一数据根。主窗口新增资料库入口，显示真实位置并可设置下次启动使用的目录；运行中不混用不同资料库。
4. 检测页首次打开后台读取全部历史，保留筛选，计数与路径可见；不触发重扫或标签写入，停止/关闭不重启。
5. SQLite增加组件schema版本、旧库一次性一致备份、原子幂等迁移及未来版本拒写保护。只增补结构，不改写旧人工结论。
6. RED→GREEN与隔离全量发布门禁；3.22.1独立目录打包，保留3.22.0。真实库不作为写测试目标。

## 明确限制

固定登记解决程序升级和存放位置变化，不代表资料库本身被搬家：数据目录必须持续保留、可访问。不同独立库自动冲突合并与媒体文件重命名迁移不纳入本次。资料库选择不应自动执行外部元数据写入。
