# 像素化：状态、视图与工作流

> 代码：`censor/review_route.py`（唯一的判定入口）、`ui/pages/censorship.py`
> 版本：v3.17.0 起

---

## 1. 为什么要重做

上一版把"有没有码"、"要不要人看"、"业务动作"三件事压进了一个概念，于是：

- 表格里一列写着 `疑似 · 待复核`、`人工确认未见`、`低风险 · 未确证` —— 语义混着；
- 筛选下拉有 9 项，其中 **「待确认」和「只看待复核」的代码完全一样**；
- 关掉程序再打开，待办列表是空的，必须手动点「加载历史记录」才找得回来 —— 这就是"遗漏"最实际的来源。

**根因**：分类不是按事实分的，是按"当时那个页面需要"堆出来的。

现在改成两个正交维度，各自只有一个来源：

## 2. 两个维度

### 结论（这个文件到底有没有码）

| 值 | 含义 | 谁能给出 |
| --- | --- | --- |
| **有码** | 画面里检出了马赛克网格 | 画面检测（置信度 ≥ 0.60） |
| **无码** | 画面里没有码 | **只有人工确认** |
| **未定** | 证据不足 | 其余情况 |

> **自动流程永远给不出「无码」。** 抽了 60 帧没找到网格，只说明"这次没找到"，
> 不构成"整片没有"的证明。这条是刻意保留的保守设计，不是缺陷。
> 最接近"无码"的自动结果叫 **低风险** —— 它是处理桶，不是结论。

### 处理（这个结果还需不需要我）

| 值 | 含义 | 算待办吗 |
| --- | --- | --- |
| **排队中** | 已导入、还没检查 | ✅ |
| **未完成** | 失败 / 取消 / 部分完成 | ✅ |
| **待复核** | 检查完了，但证据不足以下结论 | ✅ |
| **已确认** | 人工拍过板（覆盖算法） | ❌ |
| **低风险** | 抽样覆盖足够、未检出网格 | ❌ |
| **已延后** | 文件名有明确无码/破解线索，按名称延后 | ❌ |

「待我处理」= 排队中 + 未完成 + 待复核。**低风险与已延后刻意不算** ——
它们不是"做完了"，而是"现在不需要做"，所以单独放在「暂不处理」视图里，随时能翻出来。

## 3. 一个视频的一生

```
导入 ──→ 排队中 ──→ 检查中 ──→ ├─ 有码 ─┐
                              ├─ 未定 ─┼─→ 待复核 ──→ 已确认（人工）
                              │        ├─→ 低风险（自动归入，不进待办）
                              │        └─→ 已延后（名称线索，需手动授权）
                              └─ 未完成（失败/取消）──→ 重试
```

无码版检索是**另一条正交的线**（未查 / 确有 / 疑似 / 未见），
只在这部片「有码」且解析出番号时才自动发起；它不改变结论，只决定"值不值得去换"。

## 4. 界面：5 个视图 × 4 种结论

顶部只有两个下拉，都是**单选 + 实时计数**：

| 视图 | 装什么 | 什么时候用 |
| --- | --- | --- |
| **待我处理 (37)** | 排队中 + 未完成 + 待复核 | 默认工作台：打开就有活可干 |
| **全部 (205)** | 所有记录 | 刚扫完想看全貌 |
| **已确认 (19)** | 人工拍过板的 | 回头看自己判过什么 |
| **可换无码版 (12)** | 检索结果为确有/疑似 | 只想找"有得换"的 |
| **暂不处理 (44)** | 低风险 + 已延后 | 抽查一下自动放过的有没有问题 |

结论：**全部 / 有码 / 无码 / 未定**。两个维度是独立的 AND，
所以"待我处理里的有码"就是一句话的事，不需要再堆菜单项。

表格列：`文件名 | 结论 | 处理 | 无码版 | 记录来源`（标识/结构分/依据默认收起）。
结论用状态色（有码红、无码绿、未定灰），处理用另一套色（待复核橙、已确认绿），
**两列颜色不同是有意的**：一眼能看出"结论定了但还没人看过"。

## 5. 不遗漏、不重复：三条机制

### 5.1 打开页面自动接过待办

`showEvent` 第一次触发时读 `store.review_queue(limit=300)`，把待处理项铺进列表并把视图切到
**「待我处理」**，状态栏写明 `已自动载入 N 个待处理项（含历史记录）`。

以前需要手动「更多 → 加载历史记录」，关一次程序就等于把待办弄丢 —— 这是最实际的遗漏来源。

### 5.2 重复导入不重算

导入时先问 `CensorService.cached_result(path, options)`：

- **命中**（文件身份 + 分析签名都一致）→ 直接把结果铺进列表，标记「复用分析」，**不进扫描队列**；
- **未命中** → 才送进扫描队列。

所以拖同一批片子进来不会从头再扫一遍；而文件被换过（大小/修改时间变）、
配置或插件版本变过、NFO 变过，签名就不匹配，照样会重算 —— **不会因为"有缓存"而漏掉该更新的结果**。
要强制重算用「更多 → 忽略缓存重新分析」，那条路径走 `force=True`，跳过这个预检。

如果整批都命中缓存，状态栏会明确写 `N 个视频沿用上次结果，本次无需重查`，
不会出现"看着像在扫其实什么都没干"的空转。

### 5.3 检索按番号去重

「无码版」是作品级事实，同一个番号的多份副本共享一条检索结果；
已查过（无论命中还是没命中）都不会重复发起，失败后 3 次熔断。

## 7. 常见疑问

**为什么「无码」只能人工确认？**
因为"没检出"和"没有"是两件事。程序能证明"这里有码"（找到了网格），
但证明不了"这里没有"（抽样之外可能还有）。所以自动流程只到「未定 / 低风险」。

**「低风险」是不是等于没问题？**
不等于。它的定义是"抽样 ≥24 帧、完成目标 80%、≥4 种不同画面，且最高结构分低于候选阈值"。
覆盖率够但仍是抽样，所以不进待办，也不改结论。

**「已延后」为什么不算待办？**
文件名里有 `无码/破解` 线索的片子，检查价值反而低（它本来就像无码版）。
默认延后、需要时从「暂不处理」里手动勾选检查，避免它们占满待办。

**为什么两种颜色的列？**
结论是事实判断，处理是流程状态。混用一个颜色会让人以为"待复核"是一种结论。
