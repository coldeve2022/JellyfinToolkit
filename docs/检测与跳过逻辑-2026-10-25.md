# 视频像素化检查：检测逻辑与跳过规则

> 对应版本 3.22.9。只写代码里真实存在的判定，不含推测。

---

## 一、一部片是怎么被判定的

判定不是单一信号，而是**多路证据 + 融合**（`censor/service.py` → `fuse(evidence, policy)`）。

### 证据来源（按可信度）

| 来源 | 依据 | 说明 |
| --- | --- | --- |
| **人工标记**（`MANUAL`） | 你点的「有码 / 无码」 | 权重最高，压过一切自动结论 |
| **番号系列规则**（`series.rules`） | FC2 / HEYZO / 1pondo 等天生无码厂牌 | 命中即倾向"无码"，不需要抽帧 |
| **文件名规则**（`filename.rules`） | 文件名里的"无码/破解/流出/reducing mosaic" | 命中给"线索"，不足以下结论 |
| **NFO / 元数据标签** | NFO 里的 tag、genre | 同上传线索级别 |
| **画面抽帧（CV）** | 抽 N 帧检测马赛克区域 | `censor_visual_enabled` 开启时才跑；关闭时结论只会是"未定" |

### 结论与处理桶

- **结论**只表达"有没有码"：`有码 / 无码 / 未定`
- **处理桶**表达"还需不需要你处理"：`待复核 / 低风险 / 已延后 / 已完成`

两者分开，是为了让"低风险"的片子不占待复核的数量（以前混在一起，待办数永远降不下来）。

## 二、什么情况下会**跳过**（复用已有结果）

导入一批文件时，程序先对每个文件调 `cached_result()`。**同时满足以下全部条件**才复用，否则重算：

| 条件 | 具体判定 |
| --- | --- |
| 同一路径 | 按绝对路径匹配 |
| 文件没被换过 | 大小 + 修改时间一致 |
| 文件身份一致 | `file_identity`（size / mtime / inode / 首尾 hash）——**替换过版本就变** |
| 分析参数一致 | 检测器列表、抽帧数、是否抽画面、马赛克阈值 |
| 外部输入一致 | 媒体服务器标签（`server_tags`）、NFO 内容 hash |
| 没要求强制重算 | 没勾"重新分析"、也不是深检 |

**只要有一条不满足就重算。** 这条设计的目的：既不因为"有缓存"漏掉该更新的结果，也不因为"重新导入"把几百部片从头再算一遍。

---

## 三、导入文件夹 / 导入媒体库：会不会全部重算

**不会。**

两个入口都走同一条路（`_partition_reusable`）：

```
收集文件列表 → 逐个问 cached_result
                ├─ 有有效缓存 → 直接铺到列表（不抽帧、不重算）
                └─ 没有 / 已失效 → 进扫描队列
```

所以：

- **第一次导入**：全部要算
- **再导入同一批**：几乎不用算，除非文件或参数变过
- **导入媒体库**：只收集"本地能访问到的路径"，同样先过缓存

### 什么时候**一定**会重算

1. 文件被替换 / 重新编码（大小、时间、身份变）
2. 改了检测设置（开关检测器、抽帧数、画面检测、马赛克阈值）
3. 改了媒体服务器标签来源
4. NFO 被改（内容 hash 变）
5. 手动点「重新分析」或「深检」（`force=True`）

## 四、历史视频

「更多 → 历史与重新分析 → 加载全部历史」做的事是：

```
从 censor.db 读出已存结果 → 直接铺到列表
```

**完全不重算**，也不联网。它只是把以前算过的东西显示出来，方便你继续复核。

所以历史里的片子：

- 已确认（有码/无码）→ 不会再进队列
- 待复核 → 出现在列表里，等你点
- 低风险 / 已延后 → 归到对应桶，不占待复核

**要让历史重新算**，只能对选中的条目显式触发（重新分析/深检），或者改参数后自然失效。

---

## 五、低风险与「已延后」是什么意思

| 桶 | 含义 | 会不会自动再查 |
| --- | --- | --- |
| 待复核 | 有线索但证据不足以下结论 | 不会，等你 |
| 低风险 | 文件名/元数据倾向无码，或没抽到马赛克 | 不会 |
| 已延后 | 文件名有线索，但没做画面确认 | **不会自动查**，要在「检查延后视频」里勾选才查 |
| 已完成 | 已有明确结论（自动或人工） | 不会 |

「延后」这个桶是刻意留白的：有些片子文件名说"破解"但画面不一定处理干净，不自动抽帧是为了省时间；你想查的时候再勾。

## 六、性能上的实际数字（本机实测参考）

| 场景 | 耗时 |
| --- | --- |
| 已缓存，重新导入 | 约 0.01–0.05 秒/部 |
| 首次元数据检测（不抽帧） | 约 0.2–1 秒/部 |
| 抽帧画面检测（默认帧数） | 与视频时长、抽帧数相关，通常 10 秒–3 分钟/部 |

（截图里那部 `结论：未定 · 耗时 162s` 就是抽帧画面检测的耗时。）
