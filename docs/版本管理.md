# 版本管理：目录规范与发版工作流

一句话：**开发目录只有一个，每个发布版本在归档目录里各占一格，永不再改。**

---

## 一、为什么以前是乱的

同一份项目在硬盘上散着 5 份，而且**版本号互相打架**：

| 位置 | 版本 | 状况 |
| --- | --- | --- |
| `D:\...\jellyfin常用整理工具\jellyfin-toolkit` | 读不到 | 最早的工作目录，堆着 `build2/build4/dist2/dist3/dist4/build_venv` 和多个 `_backup_*` |
| `D:\...\jellyfin常用整理工具\jellyfin-toolkit-release` | **4.0.0** | 2026-09-18 的"内部首发"快照。`.git` 里**一个提交都没有**、从未推送 |
| `C:\...\WorkBuddy\2026-09-19-00-49-57\jellyfin-toolkit` | 3.6.0 | 我接手时的工作副本 |
| `C:\...\WorkBuddy\2026-09-19-09-29-14\jellyfin-toolkit` | 3.7.0 | 已发布 v3.7.0 的副本 |
| `C:\...\WorkBuddy\2026-09-19-22-30-00\jellyfin-toolkit` | **3.8.1** | 当前开发副本（最新） |

两个根源：

1. **每做一版就换一个文件夹**（`WorkBuddy\<时间戳>\jellyfin-toolkit`），旧的不清理 →
   多份并存、分不清；
2. **版本号有两套**：本地那份走到 `4.0.0`（未发布），公开仓库这边是 `3.6.0 → 3.7.0 → 3.8.x`。
   于是"版本号最高的那个"（4.0.0）**内容反而更旧** —— 它没有后来加的
   `批量生成字幕` 与 `马赛克破解` 两个页面。

> **结论：以公开仓库为准。** 仓库地址 `https://github.com/coldeve2022/JellyfinToolkit`，
> 当前最新 `v3.8.1`。本地那个 `4.0.0` 是**从未发布的内部快照**，按第 六 节处理。

## 二、三条基本规则

| 规则 | 内容 |
| --- | --- |
| **① 单一开发目录** | 只保留一个源码目录，就叫 `jellyfin-toolkit`，**永远是最新代码**。不再按时间戳建新目录 |
| **② 单一版本来源** | 版本号只写在 `version.py` 的 `__version__`（`pyproject.toml` 同步，CI 会校验一致性）。别处一律不写死 |
| **③ 一版一目录** | 每次发布，在归档目录建 `vX.Y.Z\`，把发行包/校验值/说明/可运行副本放进去，**之后不再改动** |

规则 ③ 是"能找回旧版本"的关键：归档目录里的东西**不覆盖**，
所以任何时候都能确认"v3.7.0 当初发出去的就是这个文件"。

## 三、目录规范

```
D:\常用jellyfin整理小工具\
├─ jellyfin-toolkit\                    ← 【唯一开发目录】= git 仓库，永远最新
│   ├─ main.py  config.py  version.py …      源码
│   ├─ dist\JellyfinToolkit\                 打包中间产物（可删，重新构建即可）
│   ├─ CHANGELOG.md                          更新日志（发版正文的来源）
│   └─ scripts\release_flow.py               归档/发版工作流工具
│
└─ JellyfinToolkit-releases\            ← 【发行归档】不进 git（一版 50 MB）
    ├─ INDEX.md                              ⭐ 版本总表：哪个最新、哪个能直接跑
    ├─ v3.8.1\
    │   ├─ JellyfinToolkit-v3.8.1-win64.zip       发行包（给别人/留档）
    │   ├─ JellyfinToolkit-v3.8.1-win64.zip.sha256  校验值
    │   ├─ JellyfinToolkit.exe.sha256
    │   ├─ 运行\JellyfinToolkit.exe               ⭐ 双击就能跑
    │   ├─ 本版说明.md                             这一版改了什么 + 怎么用
    │   └─ 版本信息.json                           版本/日期/大小/校验值/提交号
    ├─ v3.8.0\ …（同样结构）
    ├─ v3.7.0\ …
    └─ v3.6.0\ …
```

**命名规则**

| 名字 | 规则 | 例子 |
| --- | --- | --- |
| 开发目录 | 固定 `jellyfin-toolkit`，不带版本号 | `jellyfin-toolkit` |
| 归档根 | `JellyfinToolkit-releases`（用英文，脚本处理路径更稳） |  |
| 版本目录 | `v` + 语义化版本号，**必须与 tag 一致** | `v3.8.1` |
| 发行包 | `JellyfinToolkit-v<版本>-win64.zip` | `JellyfinToolkit-v3.8.1-win64.zip` |
| 可运行目录 | 固定叫 `运行` | `运行\JellyfinToolkit.exe` |

## 四、版本号怎么走

遵循[语义化版本](https://semver.org/lang/zh-CN/) `MAJOR.MINOR.PATCH`：

- **PATCH**（3.8.0 → 3.8.1）：修 bug、调参数、改文档；
- **MINOR**（3.8.1 → 3.9.0）：加新功能页、加新能力；
- **MAJOR**：破坏性变更（配置格式不兼容、需要用户手工迁移）。

**公开版本线**：`v3.7.0`（首个公开版）→ `v3.8.0` → `v3.8.1` → 之后继续 3.x。

> 本地那个 `4.0.0` **不纳入公开版本线**（它从未发布，内容也旧于 3.8.1）。
> 下一个公开发布建议用 **v3.9.0**，避免和它撞号。
> 以后要走到 4.x 时再统一升 —— 那时它才有意义。

## 五、完整发版工作流

### 正常发一版（7 步）

```bash
cd /d D:\常用jellyfin整理小工具\jellyfin-toolkit

# 1. 改代码、跑测试（本地全绿再往下走）
pytest -q

# 2. 升版本号（两处都要改，CI 会校验一致性）
#    version.py 的 __version__ 和 pyproject.toml 的 version

# 3. 写更新日志 —— 这一步不能省
#    CHANGELOG.md 里加一节：## [3.9.0] — 日期
#    发布页的正文就是从这里抽的，没有它发布页会是空的

# 4. 发版前检查（版本一致性 / CHANGELOG 有没有本版 / 工作区是否干净）
python scripts/release_flow.py check

# 5. 构建发行包（图标 + 版本资源 + PyInstaller + zip + SHA256）
python scripts/build_release.py --skip-tests

# 6. 归档 + 更新索引（同时解压出一份「双击就能跑」的副本）
python scripts/release_flow.py archive

# 7. 提交 → 打标签 → 推送（推标签会自动触发线上构建与发布）
git add -A && git commit -m "v3.9.0: …"
git push origin main
git tag v3.9.0 && git push origin v3.9.0
```

第 7 步推送后，GitHub Actions 会自动：构建 → 冒烟测试 → 创建 Release
（正文直接嵌入 CHANGELOG 里本版的内容）。

### 核对线上产物与本地归档是否一致

```bash
gh release view v3.9.0 --repo coldeve2022/JellyfinToolkit --json assets \
  --jq '.assets[] | "\(.name)  \(.digest)"'
# 与 JellyfinToolkit-releases\v3.9.0\版本信息.json 里的 zip_sha256 对比
```

两边是各自独立构建的，**哈希不会相同**（构建时间戳等差异），
所以对不上是正常的。要核对就看 GitHub 的 `digest` 与附件里的 `.sha256` 是否一致——
这个是必须一致的（发版流程里有校验）。

### 常见操作

```bash
python scripts/release_flow.py status                       # 看归档里有哪些版本
python scripts/release_flow.py index                        # 重建 INDEX.md
python scripts/release_flow.py archive --from-github v3.8.0 # 把线上某版拉回归档
python scripts/release_flow.py archive --zip <某zip路径>     # 归档一个外部拿到的包
```

归档根目录默认 `D:\常用jellyfin整理小工具\JellyfinToolkit-releases`，
换位置用 `--archive` 或环境变量 `JELLYFIN_TOOLKIT_ARCHIVE`。

## 七、常见问题

**Q：哪个文件可以直接双击打开？**
A：归档目录里最新版本的 `vX.Y.Z\运行\JellyfinToolkit.exe`。
`INDEX.md` 里有「直接运行」一列，最新版标着 ⭐。

**Q：我要给同事一个安装包，给哪个？**
A：`vX.Y.Z\JellyfinToolkit-vX.Y.Z-win64.zip`。对方解压后双击里面的 exe 即可。

**Q：怎么找回半年前的版本？**
A：归档目录里每个版本一个子目录，`INDEX.md` 有完整清单（含归档日期与校验值）。
如果某版只存在于线上，用 `archive --from-github vX.Y.Z` 拉回来。

**Q：归档为什么不放进 git 仓库？**
A：一个发行包约 50 MB，几版就把仓库撑到几百 MB，克隆会变得很慢。
发行包的正确位置是 **Release 附件**（线上）+ **本地归档**（这里），git 里只放源码。

**Q：改了版本号忘了写 CHANGELOG 会怎样？**
A：`release_flow.py check` 会拦住你；CI 里也有一条守则会失败。
这是刻意的 —— 否则发布页正文会是空的。

**Q：能不能不升版本号就重新发一版？**
A：不建议。GitHub 的 Release 是按 tag 组织的，同一个 tag 重发会覆盖上一次，
别人无法区分。要重发就升 PATCH 号（3.8.1 → 3.8.2）。
（唯一的例外是**发布失败**、Release 还没创建出来时，可以删掉 tag 重打。）

## 五、发错了怎么办

**Release 还没创建**（构建失败）：直接修好、把标签移到新的提交再推一次即可 ——
没有人消费过这个标签，挪动是安全的。

```bash
gh api -X DELETE repos/coldeve2022/JellyfinToolkit/git/refs/tags/v3.8.2
git tag -d v3.8.2
# 修好、提交、推送 main 之后
git tag -a v3.8.2 -m "v3.8.2" && git push origin v3.8.2
```

**Release 已经发布**：不要删标签重发（已下载的人会拿到对不上的校验值）。
**发一个新版本，在 CHANGELOG 里说明前一版的问题**，并在 GitHub 上把坏的那版标为
Pre-release 或从 Release 正文顶部加一行提示。
