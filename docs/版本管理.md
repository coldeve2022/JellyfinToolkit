# 版本管理与可验证构建

版本声明来自 `version.py`；`pyproject.toml`、CHANGELOG、Windows字符串版本和固定版本元组必须一致。开发源码与历史发行归档分开保存，历史版本不自动覆盖。

## 准备新版本

```powershell
python scripts/version_manage.py bump 3.10.0 --note "填写真实变化"
python scripts/version_manage.py check
```

修改 CHANGELOG 中的新版本小节，完成实现、测试和文档后提交。`VERSION_TUPLE` 会随提升版本同步更新，检查器也会验证固定资源元组。

## 验证和构建

构建需要 Windows、FFmpeg/ffprobe 和独立 Python 环境：

```powershell
python -m pip install -r requirements-build.txt
python scripts/build_release.py
```

构建入口先要求已提交的干净源码，再运行全套 pytest、ruff、compileall 和版本检查。验证记录包含提交、完整源码摘要、环境和每项检查结果。图标、版本资源和 PyInstaller 中间产物只写入 `build/`，不会修改已验证的跟踪源码。

已运行完整门禁时，可避免重复测试：

```powershell
python scripts/verify_release.py --receipt build/verification.json
python scripts/build_release.py --skip-tests --verification build/verification.json
```

缺少记录、源码或提交改变、检查失败都会中止。构建后会核对 exe 字符串版本与固定版本，再在隔离数据目录启动烟测；封包前再次核对源码摘要，拒绝把构建期间变化的源码声明为已验证。`--name` 只接受文件名，不能写出 `dist/`。

输出包括 onedir 运行目录、ZIP、SHA256 和 `build-manifest.json`。清单记录版本、源码提交/摘要、验证记录及 exe 摘要。启动烟测检查实际的 `data/app-error.log`，要求整个采样时长存活，缺产物会失败。

## 归档

```powershell
python scripts/release_flow.py --archive "你的发行归档目录" archive --version 3.10.0
python scripts/release_flow.py --archive "你的发行归档目录" index
```

第一次归档先在同目录暂存和校验，完整后才落位。重复归档相同 ZIP 直接返回原目录，不重建“运行”副本，不改说明、元数据或便携数据。同版本内容不同、已有归档损坏或不完整时拒绝覆盖。

线上导入必须验证下载 SHA256，历史提交来自对应标签或可信构建清单，不能冒用当前 HEAD。不安全 ZIP 路径会被拒绝。INDEX 中运行路径相对归档根目录，并把未发布快照单独列出。

## 在线发布

`release.yml` 的验证矩阵阻断后续构建，手工指定标签时所有步骤检查同一 ref。Windows 构建再生成与源码绑定的本机门禁记录、验证产物并上传附件。最终使用 `gh release create` 创建新 Release；已有 Release 会拒绝创建，不会重写旧附件。

版本提升、提交、标签和在线发布是不同动作；本地构建完成不代表已经发布到 GitHub。本地未发布构建应在归档元数据中标明 `published=false`，避免内部快照被误认成公开最新版。
