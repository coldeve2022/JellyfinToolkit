# 资料库与历史继承（3.22.1）

## 本次问题的实际原因

历史本来已保存在 SQLite，并非 BAT 临时存储。原项目 data/censor.db 有2602条扫描、1414条人工确认，默认用户目录却存在另一份4条扫描、0条确认的库。BAT只是通过data-dir指回原目录。另一个展示问题是旧启动只恢复最多300待办，已确认历史默认不自动加载。

3.22.1将资料库定位、结构迁移与页面展示分别修复。扫描结果、人工结论和版本事件继续持久保存在同一数据库中；程序版本升级不需要先导出再导入。

## 默认资料库如何固定

普通启动在用户目录保存data-profile.json，仅登记资料库的实际根路径，不保存一份与原库竞争的扫描数据。Windows通常位于%APPDATA%/JellyfinToolkit/data-profile.json。程序更换目录或版本后继续读取该登记。

已有资料库直接接续原位置，避免无必要复制大量证据、修改证据引用或产生同步分叉；新安装无旧库时使用标准用户目录。首次只检查程序有限父级和标准用户位置，不递归遍历磁盘。发现多个有数据的库时展示路径与扫描/确认数量，明确选择一次；不会按修改时间或记录多少擅自覆盖合并。已登记位置不可访问、需要的数据库缺失或登记损坏时，说明错误并提供选择已有资料库，不静默切空库。

**资料库目前可以仍在原项目目录内。不要因为更新了程序就删除该数据根目录。** 本次没有将真实数据搬到新位置；固定登记解决“程序升级后去哪读”，不是资料库删除或磁盘损坏后的自动恢复。

主窗口底部“资料库”可查看真实路径、持久数量、打开目录及选择下次启动默认。选择已有库不复制覆盖文件，重启生效，运行中不会切换一半模块。目录应为包含data子目录的上一级；直接选data子目录会拒绝。

显式--data-dir、JELLYFIN_TOOLKIT_DATA_DIR和便携模式仍优先，用于特殊部署、测试或隔离；这些启动不改写普通默认登记。因此旧BAT若一直带旧目录参数仍优先该参数，普通直接启动才使用已登记资料库。

## 自动读取与筛选

首次进入检测页自动后台读取全部历史，包含人工确认，不启动FFmpeg、重扫视频或给外部NFO/Jellyfin重新写标签。读取及呈现仍分批进行，不需每500条手动点下一批。

已保存的筛选保留。因此“数据库已保存数量”“已载入数量”“当前可见数量”可能不同；页面显示实际数据库路径与持久计数。要看所有项目，检查视图、结论、搜索、喜欢和播放筛选。停止读取只保留已呈现部分，不删数据库，也不自动重新开始。返回页面不会清空当前扫描结果。

## 数据结构如何自动升级

扫描库中的toolkit_schema_versions按组件记录结构版本，当前censor_verdict为1。旧库升级前通过SQLite backup生成包含已提交WAL的一致快照，位于数据库旁backups目录。迁移在同一事务中增补结构、继承旧人工记录并登记版本；失败整体回滚，不能写成已升级。重复启动不重复备份/迁移；遇较新不支持的组件版本拒绝写入。

原扫描、人工确认、历史、附加列和其他组件数据保留，不以空库替换旧库。算法缓存是否需要重新计算仍按文件版本和算法签名判定，与“数据库能否读取”是两回事。人工结论不会因程序版本变化直接删除；视频内容替换后旧确认不自动证明新内容。

## 数据与备份

数据根目录下config.json是设置，data/censor.db是检测与人工历史，data/censor_thumbs是证据；另外有任务/标签状态、偏好、用户快照和文件操作备份等。不要只复制一个EXE，也不要仅备份DB后删除证据。活跃SQLite应使用在线备份API或关闭程序后做一致备份，不单拷可能仍有WAL的主DB文件。

本次不自动合并两份独立库。另一个库仍保留，可从资料库入口切换。若以后确需合并，需要按文件身份、人工事件和撤回记录做明确冲突处理，不能用覆盖文件或“只留最新一行”代替。

本机已将原项目根目录登记为普通启动的固定资料库，另一份4条扫描的用户目录库未覆盖。3.22.1程序将独立输出到dist/v3.22.1/JellyfinToolkit，不依赖旧BAT；需要保留整个_internal目录。

## 验证范围

固定登记、多个库选择、显式隔离、失联/损坏处理、原子保存、页面全量恢复、停止与对象生命周期、组件迁移备份/回滚均用隔离数据回归。真实原库仅用于只读兼容核对；测试迁移在副本执行。实际启动新版后才会在所选库执行正常的结构升级。发布版本和完整门禁以对应build-manifest.json与最后成功日志为准。
