# 无码版本检索（censor/releases）

> 代码：`censor/releases/`，界面：`ui/censor_release.py` + 像素化检查页第 8 列
> 首个版本：2026-10-22

---

## 1. 它解决什么问题

像素化检查回答的是「**本地这个文件还有没有马赛克**」。
这一套回答的是另一件事：「**网络上有没有这部作品的无码版，能不能直接下载**」。

两者必须分开，因为它们的证据不能互相冒充：

| 说法 | 由谁负责 | 注意 |
| --- | --- | --- |
| 标签/文件名写着无码 | 检测子系统（弱证据） | 文件被替换过，名字往往没改 |
| 画面里检不出网格 | 检测子系统（强证据） | 抽样没覆盖到 ≠ 全片无码 |
| 这部作品有无码版 | **本子系统** | 有资源不等于你手上这份已经是 |

**它不改变检测结论。** 它只加一列「无码版」，并把"值得下载替换"的片子挑出来。

---

## 2. 四态结论（这就是"确定性"的定义）

| 结论 | 含义 | 判定条件 |
| --- | --- | --- |
| **确有** | 查到明确的无码条目 | 至少一条候选带**硬依据**（置信度 ≥ 0.8）：站点自带無碼标记 / 片商是无码厂牌 / 类别含「無碼流出」 |
| **疑似** | 只有软依据 | 某站标题里出现 Uncensored / Decensored / 破解，但没有条目级确证（置信度 0.55） |
| **未见** | 查到作品，但没有无码版本 | 有候选条目，但都不满足上面两条 |
| **未查** | 没查成 | 没解析出番号 / 所有站点失败 / 站点被拦 / 站点无此条目 |

**「未查」和「未见」必须分开。** 把"站点被墙"说成"没有无码版"，会让用户放弃一部
其实有资源的片子 —— 这是这类工具最容易犯、也最坑人的错。

界面里「未查」会带上原因（例如「站点被拦截」），鼠标悬停能看到每个站点各自的成败。

## 3. 站点现状（2026-10 本机实测）

| 站点 | 可达 | 无码判定依据 | 磁链 | 备注 |
| --- | --- | --- | --- | --- |
| **JavDB** | ✅ 稳定（需代理） | 片商 ∈ 无码厂牌 / 类别含無碼 / 番号属 FC2 等 | ✅ 详情页直接给 `magnet:` + 大小 | 主力源 |
| **JavBus** | ⚠️ 时好时坏（Cloudflare 按 URL 拦） | 站点自带 `var uc = 0/1` | ✅ ajax 接口 | 独立信源，用于互证 |
| **Supjav** | ❌ 整站 Cloudflare 挑战 | 只有标题线索（软依据） | ❌ 流媒体站 | 需要旁路服务 |

实测样本：

| 番号 | JavDB 片商 | 类别 | 结论 | 用户本地是否有无码版 |
| --- | --- | --- | --- | --- |
| PIYO-170 | ひよこ | 單體作品… | 未见 | 没有 ✅ |
| NCRA-026 | 日本コンテンツ流通（流出专营） | 介紹影片 | **确有** + 5 个磁链 | 有（无码流出）✅ |
| STARS-016 | SOD Create | …+ **無碼流出** | **确有** + 17 个磁链 | 有（`-U` 版）✅ |

三个样本的结论与实际情况全部一致 —— 这也是我把这两个站作为内置源的原因。

### 关于 Supjav：不闯 Cloudflare，改查索引

`supjav.com` 整站在 Cloudflare 挑战后面，纯 HTTP 一律 403「Just a moment...」，
配 FlareSolverr 也未必过得了（本机实测 90 秒超时）。但我们要回答的问题很窄：
**这部作品在这个站上有没有无码/破解条目** —— 这件事搜索引擎的爬虫早就做完了。

所以 Supjav 源走的是**站点索引检索**（`censor/releases/index_search.py`）：
拿 `site:supjav.com <番号>` 去 Bing / DuckDuckGo 的索引里查。实测直接命中：

```
https://supjav.com/139614.html
【無修正流出】NCRA-026 Pure Moe Mix/土屋あさみ - SupJav
```

这条路的好处不只是"能查"：

| | 直连 / 旁路抓页面 | 查索引 |
| --- | --- | --- |
| 成功率 | Cloudflare 说了算 | 稳定 |
| 依赖 | 浏览器 / 旁路服务 | 只要 HTTP |
| 速度 | 每页 3~90 秒 | 1~2 秒 |
| 可核对 | 抓到才知道 | 直接用浏览器打开链接 |

引擎顺序可配：`release_supjav_engines`，默认 `["bing", "duckduckgo"]`。
Bing 限流宽松、能直出链接；DDG 结果干净但连查几次就会要求人机校验
（实测返回 202，程序会把它记成"限流"而不是"没有结果"）。

#### 判定分两档（重要）

Supjav 上有一类介于中间的条目：`[Reducing Mosaic]`（减码/薄码版）——
码被动过，但不保证已经全无码。所以：

| 标题标记 | 判定 | 报告里显示 |
| --- | --- | --- |
| 無修正流出 / Uncensored Leak / Decensored / 破解 | 确有（0.85） | 确有 |
| Reducing Mosaic / 薄码 / 减码 | 疑似（0.60） | 疑似（需核对） |
| 没有任何标记 | 不算无码条目 | 未见 |

实测三例（2026-10-22）：`NCRA-026` → 确有（Uncensored Leak）、
`PIYO-170` → **疑似**（存在 `[Reducing Mosaic]` 版，JavDB 那边是"未见"）、
`STARS-016` → Supjav 无条目（JavDB 已是确有）。

#### FlareSolverr 还要不要装

**不需要了。** 它为这条路原本是唯一解，现在只对"确实要抓被 CF 挡住的 HTML 正文"
的场景有用。已经装在 `D:\Tools\FlareSolverr\`（端口 8191）不会影响本功能；
**把「Cloudflare 旁路地址」留空**即可，程序默认就不走它。

（如果哪天真要启用：它必须放全英文路径，且启动前要清空代理环境变量，
否则连本机调试端口也会被塞进代理、启动即崩。`start-flaresolverr.bat` 里已处理。）

### 连接自检

「检查设置 → 测试连接」会依次检查四层，逐条告诉你卡在哪：

| 检查项 | 失败时怎么修 |
| --- | --- |
| Cloudflare 旁路服务 | 双击 `start-flaresolverr.bat`，等 30~60 秒 |
| 网络线路（代理） | 在「检索代理」填能访问该站的地址 |
| JavDB 检索 | 站点改版或该番号不存在 |
| Supjav 检索 | 需要旁路，且出口 IP 要能过挑战 |

## 4. 代理策略（不写死任何端口）

优先级：**配置 `release_proxy` → 环境变量 → Windows 系统代理（读注册表）→ 直连**。

- 一条线路成功后会被**钉住**，后续请求不再逐条回退 ——
  否则一次偶发失败会连带去试其它线路，而那些线路往往"超时"而不是"快速失败"，
  实测会把单次检索从 4 秒拖到 26 秒；
- 404/410 **不重试**（重试没有意义，只会拖慢整批）；
- 403 且命中 Cloudflare 特征 → 抛 `TransportBlocked`，报告里写「被拦截」；
- 同站两次请求默认间隔 1.5 秒，单次检索最多 40 个请求 —— 别把站点打毛。

> 实测提醒：本机系统代理是 `127.0.0.1:10873`，但只有 `127.0.0.1:7897` 能通 JavDB。
> 这种情况下请在「检查设置 → 检索代理」里显式填一次。**留空才走自动探测。**

## 5. 缓存与队列

- 缓存键是**番号**（不是文件路径）：「这部作品有没有无码版」是作品级事实，
  同一部片的多个副本、多个分辨率共享一条结果；
- 默认 7 天过期（`release_cache_days`）；
- 缓存里带**签名**（源集合 + 各源版本 + 判定算法版本），
  任一变化自动失效 —— 改了判定规则不会继续用旧结论；
- 表在 `censor.db` 里，**与像素化结果完全分开**：
  清自动检测结果不会丢检索结果，反之亦然；
- `release_lookup_queue` 记录待查番号，跨次启动可续。

## 6. 自动化：怎么把人工判断降一个量级

关键不是"让程序替你看图"，而是**只让人看值得看的那一批**：

1. **你确认「有码」的片**才自动按番号去查无码版（可关）。算法猜的"疑似有码"不查 ——
   那只是猜测，拿它去查等于用假设喂流程；
2. 表格多出「无码版」一列：确有 / 疑似 / 未见 / 未查；
3. 切到视图 **「② 找替换」** —— 这里只装你标记过「有码」的片，无码版列就是检索结果；
4. 点一行，右侧面板列出候选条目（站点/片商/日期/种子数/最大体积），
   两个按钮：**打开页面**、**复制磁链**（复制的是最大那个种子）；
5. 替换完再扫一遍，结论与这一列都会刷新。

也就是说：**没有无码版的片子不必再逐个复核** —— 反正没得换。
这一条比提高检测精度更能立刻减少工作量。

## 7. 加一个站点（三步）

```python
# censor/releases/mysite.py
from censor.releases.base import ReleaseSource
from censor.releases.models import ReleaseCandidate, ReleaseQuery

class MySiteSource(ReleaseSource):
    name = "mysite"
    title = "MySite"
    homepage = "https://example.com"
    capabilities = ("http",)
    version = "1"

    def search(self, query: ReleaseQuery, *, should_stop=lambda: False,
               log=lambda _m: None, limit: int = 4):
        page = self.transport.get(f"https://example.com/search?q={query.number}")
        # ...用自己的正则/解析写这里
        return [ReleaseCandidate(source=self.name, number=query.number, uncensored=True,
                                 uncensored_reason="站点标记", uncensored_confidence=0.9)]
```

然后在 `censor/releases/__init__.py::register_builtins()` 里加一行：

```python
sources.add("mysite", MySiteSource, priority=40, title="MySite")
```

配置 `release_sources` 里加上 `"mysite"` 即生效。判定、缓存、界面都不用改。

**约定**：`search` 失败就抛异常（service 会记成"失败：原因"）；
站点明确没有这条就返回 `[]`。两者在报告里是不同的东西。

## 8. 已知限制（写清楚，免得当成 bug）

- **JavDB/JavBus 覆盖的是官方无码与流出版**。粉丝用 AI 破解的版本主要靠 Supjav，
  而 Supjav 需要旁路 —— 所以在没配旁路时，"未见"不等于"网上真的没有破解版"。
- 番号解析不出来的片子（命名混乱、只有标题）查不了，显示「无番号」。
- 检索是**逐番号串行**的，单次 4~9 秒；700 部片首轮约 1~1.5 小时（之后走缓存）。
- 磁链只做"复制"，不内置下载器。要不要下载、下哪个，由你决定。
- 站点改版会让解析失效 —— 但只会变成「未查」并显示失败原因，不会伪造结论。
