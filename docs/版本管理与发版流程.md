# 版本管理与发版流程

面向"要改代码、要发新版"的人。只想用软件的话看仓库根目录的 `版本管理说明.md`。

---

## 一、核心规则

**版本号只有一个来源：`version.py` 里的 `__version__`。**
`pyproject.toml`、`CHANGELOG.md`、git 标签都是从它派生的，必须跟着它走。

为什么强调这一点：版本混乱几乎从来不是"忘了改某个数字"，而是**同一个事实被写在了四个地方**，
漏掉一处就会出现"界面写 3.8、文件属性写 3.7、Release 叫 3.9"这种事。
所以有一条命令专门用来查它们有没有跑偏：

```bash
python scripts/version_manage.py check     # 一致 → 退出码 0；不一致 → 1
```

它会查四件事，其中前两条是**发版会直接失败**的：

| 检查 | 不同步的后果 |
| --- | --- |
| `version.py` 与 `pyproject.toml` 一致 | release workflow 的「标签与 version.py 一致性检查」直接红 |
| `CHANGELOG.md` 里有当前版本这一节 | Release 正文会是空的（正文就是从这一节抽的） |
| git 标签与 `version.py` 一致 | 打错标签会发出一个版本号对不上的包 |
| CHANGELOG 顶部版本不比当前版本新 | 只是警告，通常是"正在准备下一个版本" |

---

## 二、源码放在哪

**只有一个开发副本**：

```
<根>\dev\jellyfin-toolkit      ← 就是它，别处不再留副本
<根>\releases\v<版本>\          ← 每次发布的压缩包（含 .sha256）
<根>\latest\                    ← 最新版解压好的可运行程序
<根>\archive\                   ← 历史开发副本，只读
```

**不要按版本复制源码文件夹。** 之前项目里出现过五个副本（3.6.0 / 3.7.0 / 3.8.1 /
一个从未发布的 4.0.0 快照 / 一个更早的原始目录），没有人能一眼说出哪个是最新的 ——
副本本身就是混乱的来源。

"怕改坏"这个诉求由 git 满足，不需要复制：

```bash
git status                  # 先看有什么改动
git restore .               # 全部丢弃，回到上次提交
git restore 某个文件         # 只丢一个文件
git stash                   # 暂时收起来，稍后再取回
```

## 三、完整发版流程

### 0. 确认当前状态

```bash
cd <根>\dev\jellyfin-toolkit
python scripts/version_manage.py status
```

`status` 会一次告诉你：当前版本号、四处是否一致、有没有未提交的改动、
已经打了哪些标签、`dist/` 里有没有产物。

**未提交改动不为 0 就别往下走** —— 先提交或丢弃。

### 1. 提升版本号

```bash
python scripts/version_manage.py bump 3.8.2 --note "一句话说明这次改了什么"
```

它会：改 `version.py` 和 `pyproject.toml`、在 `CHANGELOG.md` 顶部插一段骨架，
然后打印后续命令。**它不会自动提交** —— 版本号这种一次性的事，让人先看一眼更稳妥。

版本号该涨哪一位：

| 变动 | 涨哪一位 | 例子 |
| --- | --- | --- |
| 修 bug、调参数、改文案 | 第三位 | 3.8.1 → 3.8.2 |
| 加功能、加页面（不破坏兼容） | 第二位 | 3.8.1 → 3.9.0 |
| 配置格式 / 数据目录变了，老用户需要迁移 | 第一位 | 3.8.1 → 4.0.0 |

### 2. 写 CHANGELOG

把刚插入骨架里的空条目改成实际内容。写法要求：

- **写"用户能感知的变化"**，不写实现细节（"改用 QScrollArea" 不如
  "窗口变小时控件不再挤在一起"）；
- **不写测试数量**（那属于开发过程，Release 页面没人关心）；
- 能对比就说清"原来怎样、现在怎样"。

### 3. 提交并推送

```bash
git add -A
git commit -m "v3.8.2: 一句话概括"
git push origin main
```

### 4. 打标签 —— 这一步才真正触发发版

```bash
git tag -a v3.8.2 -m "v3.8.2 — 一句话概括"
git push origin v3.8.2
```

> 标签必须与 `version.py` 一致，否则 CI 的检查会拦下。
> 推送前建议核对一下 `git ls-remote origin refs/heads/main` 与本地 HEAD 一致 ——
> 网络抖动时 `git push` 可能静默失败，而**标签却推成功了**，
> 结果就是"标签指向一个远端还没有的提交"。

### 5. 看 Actions

打开 https://github.com/coldeve2022/JellyfinToolkit/actions —— release workflow 会自动：

| 步骤 | 做什么 |
| --- | --- |
| 标签一致性检查 | 标签 vs `version.py`，不一致就停 |
| 构建 | 生成图标与版本资源 → PyInstaller → zip → 算 SHA256 |
| 冒烟测试 | 真启动一次 exe，读应用自己的错误日志（进程活着 ≠ 没崩） |
| 生成 Release 正文 | 从 CHANGELOG 抽出本版本那一节，**直接写进正文**（不是只给链接） |
| 创建 / 更新 Release | 上传 zip 与两个 `.sha256` |

全绿大约 2 分钟。红了就看失败步骤的日志 —— 常见原因是版本号没同步（回到第 1 步）。

### 6. 把产物归档到本地

```bash
cd <根>\releases
mkdir v3.8.2 && cd v3.8.2
gh release download v3.8.2 --repo coldeve2022/JellyfinToolkit --pattern "*"
```

再解压一份到 `latest\`（先清空旧的），让"双击就能用"永远指向最新版。

## 四、不想用 CI 时：本地打包

```bash
cd <根>\dev\jellyfin-toolkit
python scripts/build_release.py            # 本地产物在 dist/
```

产出与 CI 一致（同一个脚本）。差别是**本地产物没有官方校验值背书**，
对外发布仍建议走 CI，让 Release 页面的 zip 与标签一一对应。

---

## 五、发错了怎么办

**Release 还没创建**（构建失败）：直接修好、把标签移到新的提交再推一次即可 ——
没有人消费过这个标签，挪动是安全的。

```bash
gh api -X DELETE repos/coldeve2022/JellyfinToolkit/git/refs/tags/v3.8.2
git tag -d v3.8.2
# 修好、提交、推送 main 之后
git tag -a v3.8.2 -m "v3.8.2" && git push origin v3.8.2
```

**Release 已经发布**：不要删标签重发（已下载的人会拿到对不上的校验值）。
**发一个新版本，在 CHANGELOG 里说明前一版的问题**，并在 GitHub 上把坏的那版标为
Pre-release 或从 Release 正文顶部加一行提示。

## 六、命令速查

```bash
python scripts/version_manage.py status              # 当前状态与一致性
python scripts/version_manage.py check               # 只校验，可进 CI
python scripts/version_manage.py bump 3.8.2 --note "…"   # 提升版本号
python scripts/build_release.py                      # 本地打包
pytest -q                                            # 发版前跑一遍
```
