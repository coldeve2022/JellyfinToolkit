## 3. 结构性缺口与重复逻辑

以下是源码检查确认的缺口或设计问题，不能与上表的独立复现数量相加。

| 问题 | 当前证据 | 改造方向 |
|---|---|---|
| 自动检索复选框没有执行落点 | `release_auto_lookup` 只在配置及检查页初始化/赋值；扫描完成、标记、检索页均无自动调度消费者 | 明确“人工确认有码后自动入队检索”，启用时真正调度，禁用时仅入清单 |
| 详情数量设置不起作用 | `release_detail_limit` 未传给 `source.search(limit=...)`；连接检查构造了此键也没有被消费 | 所有源采用同一个有效请求选项 |
| 检索队列没有形成续跑机制 | 标记时写 `release_lookup_queue`，检索页却从标签重建全部清单，不消费 pending；失败/取消仍 done | 统一队列与任务状态，待办和事实清单分离但相互引用 |
| 检索没有进入任务中心 | `ui/pages/censor_replace.py:301` 直接 `worker.start()`，其状态、错误数、日志不被全局任务管理记录 | 作为独立只读任务注册，不阻塞其他页扫描；错误、取消不算成功 |
| 配置生命周期不统一 | 检查页内对 cfg 即时赋值，保存只 cfg.save，未广播配置事件；检索服务已初始化的 transport 保留旧配置 | 编辑副本 → 校验 → 保存 → 单次事件；各服务按配置版本重建依赖 |
| GUI 线程仍做批量文件 I/O | `_partition_reusable` 在开始后台任务前逐文件 stat、抽样 hash、NFO hash；检索页刷新逐文件开库 | 把缓存验证和批量列表查询放后台，使用分页/批量读取和批次身份 |
| 运行参数可在任务中变化 | TaskManager 复制 worker._options 等，但 CensorScanWorker._service.cfg 与页面 cfg 仍是同一对象；检索线程也持有同一个 service | 任务启动创建有效配置快照，后续结果核验快照版本 |
| 多套状态词识别产生差异 | `tag_signals.classify_tag` 有边界/否定规则；JavDB、JavBus、Supjav 使用不同子串扫描和词表 | 统一语言归一化、否定处理和作品匹配；站点特有证据强度由适配器声明 |
| 工具发现仍有平行代码 | AST 找到 `lada_tool._drives`、`whisper_tool._drives`、`tool_search.drives` 相同；两个 search_* 及 parse_options 相同 | 抽公共工具发现和 CLI 选项解析，保留工具特定名称与能力探测 |
| 通用辅助逻辑重复 | `library.split_path_name` 与 `media_types.split_path_name` 相同；v1/v2 item_features 相同循环 | 公共路径函数直接委托；特征构造接收权重，保留 v1/v2 算法差异 |
| 不能从检索串到替换 | `main.py` 只有字幕发送、Lada → 替换事件；检索页没有关联候选下载后的本地文件匹配入口 | 增加本地候选导入和人工审阅配对，复用可恢复 replacement 服务 |
| 核心两页未接媒体变更 | 无 `events.media_changed` 订阅；替换成功未更新像素化身份/结论 | 媒体变更后旧身份失效，新文件待验证，保留历史而不沿用旧结论 |
| 自动化没有这两项能力 | `automation/` 没有像素化扫描/版本检索步骤 | 在同一服务和队列上增加步骤，避免再建一套实现 |
| 个性化只停留在可拖动 | 两页可拖列宽/列序，但未持久化，检测页默认隐藏的列缺少显隐入口；检索页主体为固定比例 QHBoxLayout | 公共工作区偏好：列显隐/顺序/宽度、分隔条、密度、快捷键和复核选项 |
| 主题颜色绕过 token | 核心页硬编码 QColor，且回填未同步刷新所有状态颜色 | 统一状态到 theme token 映射，主题变化重绘 |
| 证据文件缺少生命周期 | 每次分析创建 UUID 子目录；未见缩略图引用清理、容量上限或失效回收机制 | 按数据库引用保留有效证据；失败/取消产物可清理，设置容量与清理入口 |

不能把“看起来相似”直接等同于应合并。例如番号厂牌与站点片商名单语义不同；v1/v2 排序算法、像素化结论与作品检索结论也应保留独立含义。统一的是身份、规则工具、配置与执行契约。

## 4. 速度、资源与准确性基线

测试环境：本机 Windows，项目 Python 3.13.7，`os.cpu_count()` 返回 20。输入全部为合成视频/图像，未读取用户视频。

| 项目 | 实测或直接计算 | 含义 |
|---|---|---|
| 精确取样 | 8 秒、640×360 合成片，取 24 帧输出 1280×720 灰度，约 3.50 秒，启动 25 个子进程 | 一次 ffprobe + 每帧独立 ffmpeg；进程启动和重复解码有优化空间 |
| 单帧算法 | 1280×720 噪声图，3 次约 0.176、0.176、0.187 秒 | 单帧中位数约 0.176 秒；不能直接当作真实影片吞吐量 |
| 指定 1280×720 的原始帧 | 60×1280×720×1 = 55296000 字节，约 52.7 MiB/视频 | 4 个并发约 211 MiB，仅含原始帧，不含数组、解码器、Qt 与证据图 |
| 实际默认原始帧（更正） | 配置默认 960×540，60 帧约 29.7 MiB/视频 | 原审计把基准显式输出尺寸写成默认值；此处更正，不改变原测量结果 |
| 深入扫描上限 | 600 帧约 527 MiB/视频；worker 当前实际最多 8 | 高并发与深采样组合可能仅原始帧就超过 4 GiB，应控制内存预算 |
| 合成机制基准 | 38 个图像样本，强命中混淆计数 tp=22、tn=10、fp=0、fn=2，4 个歧义样本单列 | 两个中心区域经 0.75 倍线性缩放后未达到强阈值，但分数仍大于复核阈值；不是两部真实影片漏检 |

本次没有真实完整影片基准、机械盘/NAS 对照、冷/热缓存多轮长跑，因此不承诺“提速几倍”或真实视频准确率。后续性能修改必须在相同样本、配置、有效取样数量和取消行为下比较。

优先顺序：

1. 修掉缓存误失效与队列错误，避免已做的工作再次执行。
2. 消除 GUI 前置批量 hash 与 SQLite N+1 连接/查询。
3. 流式取样分析，限制内存中等待分析的帧数；按需保留证据。
4. 测试分段取样/复用解码器或合并证据编码，保留精确时间戳；不能用 fps 复制关键帧来冒充加速。
5. 根据磁盘、CPU、内存预算管理并发。检索按 host 限速，跨 host 受控并行；重试、代理回退也经过同一调度器。
